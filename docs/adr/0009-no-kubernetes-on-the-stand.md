# Kubernetes на стенді не піднімаємо

## Context and Problem Statement

Два з трьох демо-сценаріїв говорять мовою Kubernetes: OOMKilled-рестарти і події
`BackOff` / `Unhealthy`. Бриф допускає `kind` як опцію. Питання — чи потрібен реальний
кластер, щоб агент відрізняв проблему ресурсів від проблеми готовності.

## Considered Options

* **kind у compose** — справжні події, справжній scheduling; ціна — ще один важкий
  компонент у стенді, довший старт і залежність демо від того, чи піднявся кластер.
* **Мок k8s API окремим сервісом** — ближче до реальності, ніж файл, але це власна
  реалізація чужого API, яку доведеться підтримувати заради трьох типів подій.
* **Події з `data/k8s_events.json`** — сигнатура тула така сама, якою була б поверх kind;
  агент не бачить різниці.

## Decision Outcome

Chosen option: «Події з файлу». Агенту потрібні не події кластера як такі, а **сигнал**:
`OOMKilling` відрізняє проблему ресурсів від проблеми готовності, бо на метриках вони
виглядають однаково. Цей сигнал файл дає повністю.

Сигнатура `k8s_events(service, hours)` навмисно така сама, якою була б поверх kind —
заміна джерела не зачепить жодного виклику.

### Consequences

* Good, because стенд піднімається за хвилини, а не десятки хвилин, і демо не залежить
  від здоров'я кластера.
* Good, because евали бігають на записаних подіях без будь-якої інфраструктури.
* Bad, because сценарій OOM на стенді неповний: пам'ять справді тече і контейнер справді
  вбивається по `mem_limit`, але подія про це — синтетична.
* Bad, because реальні межі k8s API (пагінація, TTL подій, права) не перевіряються;
  спливуть при переході на живий кластер.
