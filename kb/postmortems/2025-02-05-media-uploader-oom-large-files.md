# PM-2025-02-05 · media-uploader: OOM на великих файлах

## Summary
Користувач завантажив серію відео по 800 МБ. Сервіс читав файл у пам'ять цілком і падав з `OOMKilled` при ліміті 512 МБ.

## Impact
47 хвилин: 6 рестартів, під час кожного обривались усі паралельні завантаження (~40 запитів).

## Timeline
- 22:10 — перший `OOMKilled`.
- 22:15 — `FrequentRestarts`.
- 22:23 — у логах перед кожним падінням — старт обробки файлу > 500 МБ.
- 22:35 — тимчасово виставлено ліміт розміру завантаження 200 МБ.
- 22:57 — рестарти припинились.

## Root cause
Обробник читав тіло запиту повністю в пам'ять замість стрімінгу в S3. Ліміт розміру завантаження був відсутній.

## Detection
`FrequentRestarts`. RSS тут — не пилка, а різкі одиночні піки, і це відрізняє разову важку операцію від leak.

## Resolution
Тимчасовий ліміт розміру, далі — стрімінг.

## Action items
- [x] Ліміт розміру завантаження на рівні інгресу.
- [x] Стрімінговий аплоад у S3 без буферизації в пам'яті.
- [ ] Ліміт пам'яті підняти після переходу на стрімінг — не раніше.

## Lessons
Форма графіка пам'яті — діагностичний сигнал: пилка = leak, плато біля ліміту = замалий limit, одиночні піки = важка разова операція.
